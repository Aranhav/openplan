# OpenPlan

OpenPlan is an open-source, Anaplan-style connected planning platform: a Rust (axum) server with a Postgres store and a React web app, shipped as one binary.

## Layout

```
Cargo.toml          Cargo workspace (members = ["crates/engine", "crates/server"])
crates/engine/      package openplan-engine, the calculation engine (structure, formulas, recalculation, summaries, cell storage codec); no I/O, no database
crates/server/      package openplan-server, binary `openplan` (HTTP API, migrations, embedded web UI)
web/                Vite + React + TypeScript app (served by the server from web/dist)
e2e/                Playwright end-to-end tests that drive the real server
docker/, compose.yml  container image and local compose stack
docs/superpowers/   product design spec and implementation plans
```

## Commands

Server (from the repo root):

```
cargo run -p openplan-server -- serve      # needs DATABASE_URL and OPENPLAN_PUBLIC_URL
cargo run -p openplan-server -- openapi    # print the OpenAPI document; needs no env or DB
cargo test -p openplan-engine              # the engine needs no database
cargo test -p openplan-server              # export DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres first
cargo clippy --all-targets -- -D warnings
cargo fmt --all --check
```

Server configuration comes from `DATABASE_URL`, `OPENPLAN_PUBLIC_URL`, `OPENPLAN_BIND` (default `0.0.0.0:8080`; `PORT` is used on all interfaces when `OPENPLAN_BIND` is unset), `OPENPLAN_LOG` (default `info`), `OPENPLAN_TRUSTED_PROXY_HOPS` (default `0`; see `docs/deploy.md`), `OPENPLAN_DB_POOL_SIZE` (default `10`; the most database connections held open, and a request waits up to 10 seconds for a free one), `OPENPLAN_MODEL_IDLE_MINUTES` (default `30`; how long an unused model stays loaded in memory before it is checkpointed and unloaded) and `OPENPLAN_LIVE_URL` (optional, a `ws://` or `wss://` address; where browsers open the WebSocket of a model, by default `OPENPLAN_PUBLIC_URL` with `ws` or `wss`; set it only when the web app is served from another host than the API, see `docs/deploy.md`).

Web:

```
pnpm install
pnpm --dir web dev          # Vite on :5173, proxies /api to :8080; run the server with OPENPLAN_PUBLIC_URL=http://localhost:8080 and OPENPLAN_LIVE_URL=ws://localhost:5173 so the live socket goes through the proxy too (the proxy sets the socket's Origin to the backend's, http://localhost:8080, which the server checks against OPENPLAN_PUBLIC_URL)
pnpm --dir web build
pnpm --dir web lint
pnpm --dir web typecheck
pnpm --dir web test
pnpm --dir web gen:api      # regenerate web/src/lib/api/schema.d.ts from the server OpenAPI document
pnpm --dir web dlx shadcn@latest add <component>   # add a shadcn/ui component (style new-york, base color neutral)
```

Web conventions:

- Call the API through `api` and `unwrap` from `web/src/lib/api/client.ts`. `api` is typed from the generated `schema.d.ts` and has `/api/v1` as its base URL, so paths are written without that prefix (`api.GET("/setup/status")`). `unwrap` throws `ApiError` for problem+json responses.
- Query keys come from `web/src/lib/api/keys.ts`.
- `web/src/routeTree.gen.ts` (TanStack Router) and `web/src/lib/api/schema.d.ts` are generated and committed. Do not edit them by hand.
- `web/src/components/ui/` is managed by the shadcn CLI. Do not edit it by hand.
- Routes: `web/src/routes/` files stay thin and pages live in `web/src/features/<name>/`. Anything that needs a signed-in user goes under the `_app` layout route (`routes/_app.tsx`, and `routes/_app/*` for its children); its `beforeLoad` redirects to `/setup` or `/login` and puts the user on the route context as `context.me`. Auth queries and mutations (`meQuery`, `useLogin`, `useLogout`, ...) are in `web/src/features/auth/api.ts`. `/login` and `/setup` have guards too (a fresh instance goes to `/setup`; a signed-in user leaves `/login`). Always build a post-login target with `safeRedirectPath` and the `/login` search with `loginSearch` (`features/auth/redirect.ts`), and set a per-screen title with `useDocumentTitle` (`hooks/use-document-title.ts`).
- Router defaults: `createAppRouter` installs the app-wide error screen (with Try again), pending spinner and not-found page, and watches for session expiry: a 401 from any query or mutation (except a failed sign-in) clears the query cache and goes to `/login`. Do not add per-route 401 handling. Navigations that leave a signed-in page for `/login` (expiry, logout) replace the history entry so Back does not return to a page that only bounces.
- Query client: `createQueryClient()` (`lib/query-client.ts`) retries network failures and 5xx twice and never retries a 4xx. It waits as long as `Retry-After` says (at most 30 s) before a retry, so a busy server (`server.busy`, 2 s) is not asked again at once.
- Live updates: `ModelLayout` follows the open model with `useModelLive(modelId)` (`features/live/`), once the model's own query has data (a pending or gone model asks for no ticket), and shares the status (`connecting`, `live`, `reconnecting`, `off`) through `LiveStatusContext`; `LiveIndicator` shows it in the module header (each state has an icon of its own, and a polite announcement for a lost, restored or given-up connection, not for the first connect). The hook gets a ticket (`POST /models/{id}/live/ticket`), opens the socket and reads again what the messages touch, gathered over 100 ms into one pass: on `cells_changed` the views whose loaded `line_items` or filters (`pivotOfKey` in `lib/api/keys.ts`) name a changed line item (the formula problems of a line item come with the structure document, so only a structure change refreshes them), on `structure_changed` the structure and every view, on `resync`, or on a reconnect whose `hello` is past the highest `seq` heard, everything of the model. Views are read again with `cancelRefetch: false`, so a read under way is let be and checked by its `seq` when done; the first `hello` also reads again the views older than it and the structure and lists loaded before the socket was asked for. `seq` is one log for all models and each changed cell takes a number too, so the numbers are never compared for gaps. It reconnects with a new ticket after 1 s, twice as long after each failure up to 30 s, with 20 % jitter; a 429 on the ticket is waited out silently for its `Retry-After` (at most 2 minutes, plus up to 20 %); a socket the browser will not make (`SecurityError`, which `console.warn`s why) or a close with 4403 or 4404 or a ticket refused with 401, 403 or 404 stops it, and all but the first read the model again so that the not-found screen takes over, unless the user just deleted the model (`mutationKeys.deleteModel`). In tests `setup.ts` puts `FakeWebSocket` (`test/live.ts`: `FakeWebSocket.last.receive(message)`, `.drop(code)`; it refuses any address but a model's live socket) in place of the socket and answers the ticket afresh for each test, so no test reaches a network.
- App shell: `routes/_app.tsx` wraps every signed-in page in `AppSidebar` (workspace switcher, nav, user menu) and `SiteHeader` (breadcrumb, `CommandMenu` on Ctrl/⌘+K); pages render their own content in the `<Outlet />`. Start a page with `PageHeader` (it also sets the tab title) and use `EmptyState` / `ErrorState` (`components/`) for empty and failed data views. `useCurrentWorkspace()` (`hooks/`) resolves the workspace from the address, the open model, the last one used (`localStorage["openplan.lastWorkspace"]`, see `lib/last-workspace.ts`) or the first one; `/` redirects there from `beforeLoad`. An address that names a workspace the user is not in resolves to none (never to another one), and its page shows `WorkspaceNotFound` (`features/workspaces/`). Workspace and model queries and mutations are in `features/workspaces/api.ts` and `features/models/api.ts`; `useWorkspaces()` reads the workspace list from the `me` query (the same data as `GET /workspaces`), so workspace mutations invalidate `me`.
- Models: the pages are `features/models/models-page.tsx` (`/w/$workspaceId`) and `features/models/model-page.tsx` (`/m/$modelId/settings`, the model settings). `/m/$modelId` is a layout route: `routes/_app/m/$modelId/route.tsx` renders `ModelLayout` (`features/build/model-layout.tsx`), which shows `ModelNotFound` (`features/models/model-not-found.tsx`) for a model that is gone (`useModelNotFound` is in `features/models/api.ts`); its index redirects to `modules`. The Build navigation is one list, `BUILD_GROUPS` in `features/build/build-nav.ts`: Lists, Time, Versions and Modules under Structure, then Model settings under Model. It feeds the Build sidebar (`features/build/build-sidebar.tsx`, shown by `AppSidebar`), the palette's "Model" group (`features/build/model-commands.tsx`, which also offers the model's lists, modules and line items) and the breadcrumb (`components/site-header.tsx`, which also names a module or a list). Only builders and admins create, rename and delete models, so gate those controls on `canEditModels(workspace.role)` (`features/workspaces/roles.ts`) and show planners and viewers plain text. A dialog opened from a button or menu item instead of a Radix trigger has nothing to hand focus back to: use `useRestoreFocus()` (`hooks/`). `relativeTime()` (`lib/format.ts`) words timestamps like "2 hours ago".
- Structure: structure queries and mutations live in `features/structure/` (`api.ts`, `types.ts`). `types.ts` exports `StructureDto`, `ModuleDto` and `LineItemDto` once. `GET /models/{id}/structure` carries `month_labels`, and every screen uses them. Each line item in it also has `formula_errors`, what the model found wrong in its formula (a name that was deleted, say; empty when it is fine or there is none), read from the same snapshot as the document: the Blueprint's error mark, the line item sheet and the formula bar read it from there, so a structure change refreshes it. The only exception is the Time screen's preview of an unsaved calendar, which uses `monthLabelsFor` in `features/time/timeline.ts`; `timeline.test.ts` pins its labels to the ones the engine gives.
- Shared structure screen pieces: reuse these, don't copy them. `DeleteDialog` (`components/delete-dialog.tsx`) and `RowDeleteButton` (`components/row-delete-button.tsx`); `ProductionNotice` and `ProductionLock` (`components/production-lock.tsx`; a control that production mode switches off sits in a `ProductionLock`, with `className="flex"` for a menu item, so that hovering it says why: the module, Blueprint, lists, time and versions screens and the formula bar all do); `useStructureAccess` (`hooks/use-structure-access.ts`), which returns `canEdit` (the role gate), `locked` (production mode) and `isLoading` (the role is not known yet); `useRemovalFocus` (`hooks/use-removal-focus.ts`; the page heading it falls back to, and the one of the Blueprint, the members table and the model page, comes from `useHeadingFocus`: `PageHeader` hands its `h1` to the `HeadingFocusProvider` in `routes/_app.tsx`, and nothing searches the document for it; a title drawn through `renderTitle` is given the ref to put on its `h1`); `useSheetDismiss`, `DiscardChangesDialog` and `focusFirstField` (`hooks/`, `components/`, `lib/sheet-focus.ts`) for a sheet whose form can lose edits; and `structureNameSchema` (`lib/validation.ts`); and `InlineText` (`components/inline-text.tsx`), text that turns into an input on a click or Enter (Enter saves, Escape cancels, blur saves). A dialog or sheet that holds one passes `isEditingInlineText` (`lib/inline-text.ts`) from its `onEscapeKeyDown`, or the first Escape would close the layer.
- Lists: the pages are `features/lists/lists-page.tsx` (`/m/$modelId/lists`) and `list-page.tsx` (`/m/$modelId/lists/$listId`). The Items tab reads a list's items, and those of its parent list, with `useListItems` (`features/lists/api.ts`, `GET /models/{id}/lists/{list_id}/items`); its key sits under the structure's, so every structure mutation reads it again. The list's settings and subsets come from the structure document. A list with a parent list needs a parent for every item, and the table groups the items under the parent list's items (`tree.ts`). The engine refuses to delete an item while items of a child list have it as their parent, so the screen blocks that and names the child items (`hierarchy.ts`) instead of promising a cascade. A table or list of more than 500 rows is windowed (`virtual.ts`) on rows of a fixed height. `ParentPicker` chooses a parent item by searching. A key pressed in its popover bubbles through the portal to the row, so a row handler for Enter or Escape must check `event.currentTarget.contains(event.target)`. Tests serve the lists, items and subsets endpoints from a fake server, `serveLists` in `web/src/test/lists.ts`, and open a screen with `openListsApp(path, { role, mode, structure })` from the same file.
- Modules: the pages are `features/modules/modules-page.tsx` (`/m/$modelId/modules`) and `module-page.tsx` (`/m/$modelId/modules/$moduleId`). The module route (`routes/_app/m/$modelId/modules/$moduleId.tsx`) keeps the tab (`grid` or `blueprint`, `grid` by default), the selected line item (`li`) and the saved view of the grid (`view`; none is the module's default view) in the address, and selecting a line item replaces the history entry instead of adding one. A module opens at its default saved view, else at `defaultView` (`default-view.ts`: line items down the rows, Time across the columns or else the first axis, the other dimensions on pages at their default member). `module-grid.tsx` passes `gridReference` (`grid-reference.ts`: the items of every list and every period) to the cell editors, and sizes itself with `useFillViewport` (`hooks/use-fill-viewport.ts`), so the grid takes the room the window leaves below it, at least 384 px.
- Grid toolbar and saved views: `ModuleGrid` (`features/modules/module-grid.tsx`) reads the module's saved views (`useSavedViews`, `features/grid/toolbar/views-api.ts`) and gives each view of each module on screen a `ViewSession` (keyed by module and view), which holds the view as a `ViewDefinition`: what the user changed on screen (`edits`) or else the saved definition, so a view nobody changed follows a refetch (an action that leaves the view as saved clears `edits`). Changes that name a dimension, a deleted member or a deleted line item no longer fit the module and are dropped (`stillFits`, `knownKeys`); the formulas typed in the formula bar are kept by `ModuleGrid` (`formula-drafts.ts`), since the session and its bar are rebuilt for each view. `view-state.ts` is the pure reducer (`reduceView`: move a dimension, swap, set a page, summaries, collapse, hide, filters, conditional formats, column widths) with `isModified` (absent, null and empty fields and the order of sets do not count) and `queryOf`; the rows are never empty, so the last dimension of the rows stays. `GridToolbar` (`features/grid/toolbar/`) puts the pivot popover (dnd-kit zones, and a menu on each chip for the keyboard), a selector for each page (`Select` up to 20 members, `Popover` and `Command` beyond), the filter and show/hide popovers, the summaries toggle, the conditional formatting `Sheet` and the saved views in one row; when everything on the row (measured, with margins and gaps, by `useToolbarFit`, with or without page selectors) is wider than the room, filter, show/hide, summaries and formatting go into a More menu (one icon) whose items open the same panels (a `ToolbarPanel` without trigger hangs from the More button); the row wraps, and the selectors wrap in their box, where it is still too narrow, so that nothing is clipped, covered or scrolled sideways. Changes that are not saved are kept in `sessionStorage` per module and view (`view-draft.ts`, every call in try/catch, a draft that is not a view of the module as it is now is ignored) and given up when another view of the module is chosen, however it is chosen. A view in the address that is not there falls back to the default with a toast. Only builders and admins save, make a view the default and delete (`canSaveViews`; production mode does not lock views). The saved views and the members of a dimension (`POST /members`, `useDimensionMembers`; a failed read shows its cause with Retry, `ToolbarError` in the row) sit under the structure's query key, so a structure change or a resync reads them again. `useRowInfo` reads the members of the row dimensions before the grid draws, so that the row headers are sized and indented from them (`rowInfo`, `rowDimInfo`) and nothing shifts as blocks arrive; the corner (`corner`) names the dimensions and widens the headers to fit its name.
- Blueprint: `features/modules/blueprint.tsx` lists a module's line items in the order of its grid (`blueprint-table.tsx`) beside `line-item-sheet.tsx`, the settings of one line item. `AddLineItemDialog` (`add-line-item-dialog.tsx`) adds a line item: it takes the id of the module, or of a list for the properties of a list, `insertAfter` to put the new one below the selected one, and `copy` to say "property" instead of "line item". A change that clears typed values is confirmed in `ClearValuesDialog` (`clear-values-dialog.tsx`), as the line item sheet and the module settings sheet do. The Blueprint's `canEdit` and `locked` props decide whether it can add, reorder and delete line items; production mode turns them off.
- Formula editor: `features/formula/` has `FormulaEditor`, a CodeMirror 6 editor (one line that grows to six; Enter submits, Shift+Enter breaks the line, Escape cancels, or first closes the list of completions). The server counts the span of a problem in UTF-8 bytes and the editor counts UTF-16 units: convert with `byteToUtf16` (`offsets.ts`). `scan.ts` is the one lexer, `language.ts` colours the tokens (with `--formula-*` in `index.css`, not hex, so light and dark both read well), `completion.ts` asks `GET /formula/completions` (150 ms after typing, kept per prefix under the structure's query key, so a structure change makes it stale; the server's order and matching stand), `lint.ts` asks `POST /formula/check` (300 ms after typing, which must hold whatever the parent re-renders: the editor watches the content of `known`, never the object, and tells the linter through a `refreshLint` effect that waits out the delay; a formula the server has already said something about, `known`, is not asked again; F8 and Ctrl+Shift+M reach the problems from the keyboard, and a check's problem count is announced when it changes, counting from the problems already marked from `known`) and `signature.ts` shows the signature of the function being called (`GET /formula/functions`, read once). It needs `modelId` and `lineItemId` (without a line item, nothing is asked of the server), and a read-only editor can be focused, selected and copied but not changed (`aria-readonly`), and asks nothing. The list under the formula is for the formula as it stands (what the server said of the saved formula, of a refused save (announced), or what the last check said): it goes while the formula is edited and returns once it is checked again, and never depends on the focus, since a list that appeared as the editor is left would move what a click was aimed at; the marks in the formula itself stay. In a form use `FormulaField` (`modules/formula-field.tsx`); a sheet or dialog around an editor calls `closeEditorPopupOnEscape(event)` (`escape.ts`: it closes the list of completions, or the panel of problems when the key is pressed in it) from its `onEscapeKeyDown` and ignores the key when it returns true. `FormulaBar` (`modules/formula-bar.tsx`) is above the Blueprint and the grid: the Blueprint's selected row or the grid's active cell (`onSelectLineItem`) drives it, what was typed is kept for each line item until it is saved or given up, and a formula for an input line item is confirmed first, since it clears the values typed into it, and the focus returns to the formula after the dialog, Save and Cancel, and after a save only if the user did not move on to another line item or a grid cell while it ran. A check, suggestions or signatures that cannot be had are said under the formula (`role="status"`; each is told apart, and none is said of a read-only editor), and a failed read of the functions is not repeated at every key.
- Platform: `isMac()` (`lib/platform.ts`) picks the shortcut hints, such as ⌘ or Ctrl.
- Members, users and profile: the pages are `features/workspaces/members-page.tsx` (`/w/$workspaceId/members`), `features/users/users-page.tsx` (`/admin/users`; anyone who is not an instance admin gets a "no access" empty state, not a redirect) and `features/profile/profile-page.tsx` (`/profile`). Only workspace admins add, remove and change members (`canManageMembers`, `features/workspaces/roles.ts`). A member who leaves a workspace (the self row says "Leave workspace") goes through `useRemoveMember(wsId, { leaving: true })`, which moves them to another workspace before the workspace list is refreshed (refreshing first would flash "workspace not found"); an instance admin is an admin of every workspace, so for them leaving is an ordinary removal and they stay on the page. Changing your own role is confirmed first. Dialogs that run a mutation ignore Escape and outside clicks while it is pending. `reportFormError(form, error, codeFields)` (`lib/form-errors.ts`) shows a server refusal under the input it names (a code-only refusal such as `user.email_taken` goes under the input `codeFields` maps it to) and falls back to a toast; `lib/validation.ts` has the shared zod fields (email, person name, password) and `rateLimitMessage` (`features/auth/rate-limit.ts`) words a 429 ("Too many attempts. Try again in 3 minutes."). With react-hook-form's `values` + `resetOptions.keepDirtyValues`, call `reset(saved, { keepDirtyValues: false })` after a save, or the options keep what was typed.
- Errors: `unwrap` throws `ApiError` (`status`, `code`, `detail`, `errors`, `retryAfter` in seconds from `Retry-After`, and `formulaErrors`, every problem of a formula the server refused, with its byte span). A fetch that never reaches the server becomes an `ApiError` with status 0 and code `network`. Use `errorDetail(error)` for text to show in a toast.

Web testing:

- Tests are Vitest with jsdom, Testing Library and `@testing-library/user-event`; the setup file is `web/src/test/setup.ts`.
- API calls are mocked with msw (v3), not by stubbing `fetch`. `web/src/test/server.ts` exports the shared server; the setup file starts it with `onUnhandledFrame: "error"` (any request without a handler fails the test) and resets handlers after each test. Add handlers per test with `server.use(http.post("/api/v1/auth/login", () => ...))` and build error responses with `problem()` from `web/src/test/problem.ts`.
- Vitest runs with `clearMocks: true`, so `vi.fn()` call counts reset between tests.
- `renderWithProviders(ui)` from `web/src/test/render.tsx` renders a component inside a query client and an in-memory router at `/host`; any other path renders a placeholder, so assert navigation with `router.state.location.href`. To test the real route tree use `renderApp(path)` and `mockSession({ needsSetup, signedIn, me })` from `web/src/test/app.tsx` (`me` is what the signed-in user and their workspaces look like; the returned session object can be changed mid-test, e.g. to sign out). `renderApp` includes the `ThemeProvider`; `makeModel()`, `workspace`, `globex` and `meInTwoWorkspaces` are ready-made fixtures. `mockSession` serves an empty model list for every workspace; `serveModels(models)` replaces it with the model endpoints (list, get, patch, delete) backed by a store the test can change (call it after `mockSession`). jsdom does not register pointer clicks on Radix submenu items, so open submenus and choose items with the keyboard (`ArrowRight`, `ArrowDown`, `Enter`).
- Mock `sonner` with `vi.mock("sonner", () => ({ toast: { error: vi.fn() } }))` when a test asserts on a toast.
- `makeStructure` is in `web/src/test/structure.ts`, and `serveStructure` in `web/src/test/app.tsx`. The shared axe helper is `violations()` in `web/src/test/axe.ts`; reuse it, don't copy it.
- Saved views and members: `serveViews(views)` and `serveMembers(membersOf)` (`web/src/test/views.ts`) serve the views of every module (create, change, delete as the server does, with `structure.name_taken`) and `POST /members`; `mockSession` answers both with nothing until a test does. `renderOverView(initial, ui)` (`web/src/test/toolbar.tsx`) renders a toolbar control over a view that its actions change, and tells the view and the actions. `spinning(button)` (`web/src/test/spinning.ts`) is the one check that a button shows its spinner. `use-view-data.test.tsx` holds the clock for the 80 ms of settling (`freezeClock`, `until`, `pass`): fake only `setTimeout`, and let React Query notify through a microtask.
- Module tests use `serveModuleStore(structure)` (`web/src/test/module-edits.ts`), which serves the structure and the endpoints that change modules and line items the way the server does. `store.formulaErrors` sets what is wrong with each line item's formula as the structure says it, `store.checkFormula` gives the problems the server finds in a formula it is asked to save or to check (`POST /formula/check` is served too, and the completions and functions as empty lists; override them with `server.use` after the store), `store.requests` lists the changes sent, and `store.hold()` makes changes wait so that a test can look at a save in progress.
- CodeMirror under jsdom: `test/codemirror-setup.ts` (a second vitest setup file) stubs the rectangles of ranges, which jsdom has no layout for. Tests set a formula with `setFormula(input, text)` and read it with `formulaText(input)` (`test/formula.ts`; `input` is the labelled textbox), and a list of completions ignores keys for 75 ms after it opens, so a test waits that long before pressing Enter or Escape.
- Component tests that draw a whole grid or page load through msw and can exceed the default 5 s under load, so they set `vi.setConfig({ testTimeout: 20_000 })` at the top of the file, as `features/grid/grid.test.tsx` does.
- E2E helpers: `createModuleViaApi` is in `e2e/tests/helpers.ts`; `breadcrumbProblems` is local to `e2e/tests/layout.spec.ts`.

End to end and containers:

```
pnpm --dir e2e test         # run `pnpm --dir web build` and `cargo build -p openplan-server` first
docker compose up --build   # OpenPlan on http://localhost:8080 with Postgres
```

- E2E (`e2e/`, Playwright pinned to 1.56.1): `playwright.config.ts` starts the real server through `scripts/start-server.sh`, which drops and recreates the port's database on the admin connection from `E2E_ADMIN_DATABASE_URL` (default `postgres://postgres:postgres@localhost:5432/postgres`): `openplan_e2e` for the default port 8090, `openplan_e2e_$E2E_PORT` for any other `E2E_PORT`. It runs `target/debug/openplan` on `127.0.0.1:$E2E_PORT` (default `8090`). Each port has its own database, so set `E2E_PORT` to run a second suite beside another on the same Postgres. A debug build reads `web/dist` from disk, so after a UI change only `pnpm --dir web build` is needed, not a server rebuild. The specs share that one instance and run on one worker: the `setup` project is `onboarding.spec.ts`, which creates the `ADMIN` user and the "Acme Corp" workspace (`tests/helpers.ts`), and the `app` project depends on it, so every other spec starts with `login(page, ADMIN)`. Never run `playwright install` locally (browsers come from `PLAYWRIGHT_BROWSERS_PATH`); CI runs `playwright install --with-deps chromium`.
- E2E specs find things by role and label and assert the copy the app really shows, so a copy change in `web/src` needs the matching spec change. `screenshot(page, name)` saves `e2e/screenshots/<name>-light.png` and `-dark.png` (gitignored, uploaded by CI); it reloads the page to apply each theme, so pass a `reopen` callback for UI a reload closes (the command palette), and `fullPage: false` for a menu that closes when the window is resized (a whole-page picture resizes it).
- CI (`.github/workflows/ci.yml`): `rust` (fmt, clippy, tests against a Postgres service; it also runs the engine's timing tests in release mode with `cargo test --release -p openplan-engine --test recalc -- --ignored`), `web` (lint, typecheck, test, build, and a `gen:api` check that `schema.d.ts` is up to date, which needs the Rust toolchain), `e2e` (needs both) and `docker` (builds `docker/Dockerfile` without pushing).
- `docker/Dockerfile` builds the web app, then the server with `web/dist` embedded, then a slim non-root runtime. The pnpm version everywhere (Dockerfile through corepack, CI through `pnpm/action-setup`) is the `packageManager` field of `web/package.json`; the workspace filter there is the path `./web...` because the package is named `openplan-web`. It does not set `OPENPLAN_BIND`, so the server follows `PORT` on Render and defaults to `0.0.0.0:8080` elsewhere; `compose.yml` sets `OPENPLAN_BIND` itself.

## Server conventions

- A handler that works on a model gets the model's actor from `handle_for(state, user, model_id, min_role, ProdLock)` (`structure_api.rs`) before it looks at anything else: it is the one place that checks membership (404), role (403) and, for `ProdLock::Enforce`, the production lock (409), so each handler states the role it needs and whether the lock applies. A route with a large body takes the caller and the actor in an extractor of the request head ahead of `ApiJson` (`Planner` in `cells_api.rs`, `Viewer` in `structure_api.rs`, which also gives the caller's role), so a caller who may not call it is refused before the body is read. A list in such a body is typed `Capped<T, N>` (`extract.rs`), which keeps the first `N` elements and only counts the rest, so the handler refuses a list that is too long without having made room for all of it: a coordinate of three bytes (`"",`) takes 32 in memory. The limits are 100,000 edits, 10,000 cells and `MAX_MODULE_DIMENSIONS` (16, the engine's limit on the dimensions of a module and so on the coordinates of a cell) coordinates to a cell. `tests/cells_memory.rs` holds the peak of such requests to 200 MB.
- A change to a model is a batch of engine commands made inside the model's actor: `handle.apply_with(user.id, |model| ...)` builds the commands from the model the batch is applied to, and `apply_with_answer` also returns what the handler answers with. Never read the model and then apply, since a batch applied in between would be missed.
- Heavy work takes a permit from `AppState.work` (`work.rs`: 4 at once, a request waits 10 s and then gets 503 `server.busy`): the view query, members and `cells/read` take it after the caller is checked and the body read, and move it into their `spawn_blocking` closure. The view query (`query_api.rs`) keeps the rows that pass a view's filters in the process-wide `PassingStore` (`view_cache.rs`, 64 MiB counted by real capacity, least recently used first across models, dropped by the actor at each batch), and a view that is not kept is read by one request while the others wait for it (`PassingCache::flight`, awaited before the permit is taken). The live socket (`live.rs`) is opened with a one-use ticket from `POST /models/{id}/live/ticket`, not with the session cookie, and checks the `Origin` against `OPENPLAN_PUBLIC_URL`; a user has at most 20 tickets and 20 sockets, a socket is closed after two pings with no word from the client and after more than 20 client frames in 10 seconds.
- Take bodies, query strings and path parameters through `ApiJson`, `ApiQuery` and `ApiPath` (`extract.rs`), not axum's `Json`, `Query` and `Path`: their rejections are `application/problem+json`, and they refuse the NUL character, which Postgres cannot store.
- Every migration that creates a table enables row level security on it (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`), because Supabase exposes the public schema through its Data API; a test in `tests/health.rs` fails for a table without it.

## Agent model policy (this project only)

OpenPlan is built by a controller session acting as architect, plus subagents. To keep cost down, every subagent dispatch names its model explicitly; no subagent inherits the controller's model.

| Role | Model | Use for |
|---|---|---|
| Architect / controller | Opus | Specs, implementation plans, rulings, dispatch, reading review verdicts. Never writes product code. |
| Implementer, complex | Sonnet | Engine algorithms (evaluator, recalc, functions with tricky semantics), concurrency and persistence (actors, checkpoints), security-sensitive server code, UI screens where UX polish matters, E2E suites. |
| Implementer, mechanical | Haiku | CRUD endpoints that copy an existing pattern, config and deploy files (Docker, CI, render.yaml, vercel.json), docs and README, test-only additions, small single-file fixes. |
| First review of a task | Sonnet | Spec compliance + code quality gate for every task. |
| Scoped re-review of a small fix | Haiku | Fix diffs under ~40 KB that touch a few files; Sonnet when the fix restructures logic. |
| Final whole-milestone review | Sonnet | One pass per milestone before merging to `main`. |

Rules: implementers never spawn subagents; fixes are new commits (never amend); stage files by explicit path; the implementer writes its report to the file named in its dispatch.

Testing cost (every task keeps writing tests; this limits how often they are run and re-checked):

- Implementers run only the tests relevant to what they are changing while they work, then the full suite once before writing the report, and quote only the summary lines.
- Reviewers run the suites once. Extra deep checks (building every commit on its own, deliberately breaking code to prove a test catches it, re-running tests to look for flakes) are only for security- and concurrency-critical code: authentication and sessions, the live-update sockets, model actors and the calculation engine. Never for UI screens, docs or config.
- CI on the pull request is the final full gate.

Context cost (what reaches the chat stays in context for the rest of the session):

- Quiet test and check runs. Every test, lint, typecheck, clippy, build or e2e run writes its full output to a log file under `.logs/` (git-ignored, e.g. `.logs/server-tests.log`). Only one result line plus the failures (names and their first error lines) reach the chat. Never print a whole run. Use `scripts/quiet.sh <name> -- <command>`, which does exactly this, e.g. `scripts/quiet.sh engine-tests -- cargo test -p openplan-engine`.
- Wide searches go to a subagent. The controller sends broad searches and research (sweeping many files, reading docs, comparing options) to a subagent with its model named. Only the conclusion comes back to the main thread, never file dumps. Read a file directly only when you already know which file and which part.
- Compact early. The controller compacts the session when its context reaches about 40%, and at the latest at each milestone boundary. The controller cannot see an exact percentage, so it asks the owner to run `/compact` at those points. The ledgers in `.superpowers/sdd/` keep the state across compactions.
